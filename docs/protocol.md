
# 聊天协议说明（阶段一）

版本：v1.0  
日期：2026.10.04
适用阶段：阶段一（命令行聊天）  
作者：ZhouJiale

---

## 1. 概述

本协议用于 C++ 聊天软件中服务端与客户端之间的通信。  
底层使用 TCP，传输的是字节流。  
为了在字节流中区分一条条独立的消息，本协议自定义了帧结构。

设计目标：

- 消息边界清晰，接收方可以准确判断一条消息何时结束。
- 支持多种消息类型，且以后扩展新类型时不需要修改已有逻辑。
- 能拒绝畸形输入，保护服务端内存，不崩溃。
- 文本统一使用 UTF-8，便于调试和跨平台。
- 为阶段三文件传输预留扩展空间。

---

## 2. 帧结构

每条消息的封装格式如下：

| MAGIC  | VERSION | TYPE | LENGTH | PAYLOAD |
|---|---|---|---|---|
| 2 B    | 1 B     | 1 B  | 4 B    | LENGTH 字节 |

说明：

| 字段 | 字节数 | 说明 |
|---|---|---|
| MAGIC | 2 | 固定为 `0x43 0x4C`（ASCII 字符 "CL"），用于快速识别本协议 |
| VERSION | 1 | 协议版本，当前为 `0x01` |
| TYPE | 1 | 消息类型，见第 3 节 |
| LENGTH | 4 | PAYLOAD 的字节数，**大端序**，不包含头部 8 字节 |
| PAYLOAD | LENGTH | 负载内容，UTF-8 JSON 字符串；阶段三文件传输时可以是二进制 |

### 2.1 头部固定长度

头部固定为 **8 字节**：

- MAGIC：2 字节
- VERSION：1 字节
- TYPE：1 字节
- LENGTH：4 字节

接收方先读取 8 字节头部，解析出 LENGTH，再读取 LENGTH 字节的 PAYLOAD。

### 2.2 字节序

LENGTH 字段使用**网络大端序**。

- 发送方：`htonl(length)`
- 接收方：`ntohl(length)`

### 2.3 长度上限

- **协议层上限：4 MiB（4 × 1024 × 1024 字节）**
  - 如果 LENGTH 超过 4 MiB，直接关闭连接，不回复。
  - 目的：防止对方报一个天文数字长度，导致服务端分配巨大内存。
- **业务层上限：1 MiB（1 × 1024 × 1024 字节）**
  - 指的是单条消息内容（如聊天内容）的最大长度。
  - 超过业务层上限时，回复 ERROR 1005，不断开连接。

### 2.4 非法帧处理

| 情况 | 处理方式 |
|---|---|
| MAGIC 不匹配 | 关闭连接 |
| VERSION 不认识 | 关闭连接 |
| LENGTH > 4 MiB | 关闭连接 |
| JSON 解析失败 | 关闭连接 |
| TYPE 不认识 | 回复 ERROR 1007，不断开连接 |

## 3. 消息类型

编号约定：

- `0x01 ~ 0x7F`：客户端 → 服务端请求
- `0x81 ~ 0xFF`：服务端 → 客户端响应/通知
- `0x10 ~ 0x1F`：为阶段三文件传输预留

### 3.1 客户端 → 服务端

| 类型 | 编号 | 作用 | PAYLOAD 字段 |
|---|---|---|---|
| LOGIN | 0x01 | 登录 | `{"username": "..."}` |
| LOGOUT | 0x02 | 主动退出 | `{}` |
| LIST | 0x03 | 请求在线列表 | `{}` |
| BROADCAST | 0x04 | 群发 | `{"content": "..."}` |
| PRIVATE | 0x05 | 私聊 | `{"to": "...", "content": "..."}` |
| FILE_SEND | 0x10 | （预留）发文件 | 待定 |
| FILE_ACK | 0x11 | （预留）文件确认 | 待定 |

### 3.2 服务端 → 客户端

| 类型 | 编号 | 作用 | PAYLOAD 字段 |
|---|---|---|---|
| LOGIN_RESP | 0x81 | 登录响应 | `{"ok": true, "reason": "..."}` |
| LIST_RESP | 0x82 | 在线列表 | `{"users": ["...", "..."]}` |
| BROADCAST_RECV | 0x83 | 收到群发 | `{"from": "...", "content": "..."}` |
| PRIVATE_RECV | 0x84 | 收到私聊 | `{"from": "...", "content": "..."}` |
| SYSTEM | 0x85 | 系统通知 | `{"content": "..."}` |
| ERROR | 0x86 | 错误 | `{"code": 1004, "message": "..."}` |
| FILE_RECV | 0x90 | （预留）收文件 | 待定 |

### 3.3 扩展性说明

- 新增消息类型时，老代码在 `switch` 的 `default` 分支回复 ERROR 1007，不会崩溃。
- 阶段三文件传输复用同一帧结构，TYPE 使用预留编号，PAYLOAD 可以是二进制。
- 心跳功能暂不实现，后续可增加 HEARTBEAT 类型，不影响已有协议。

## 4. 错误码

ERROR 消息的 PAYLOAD 格式：

```json
{
  "code": 1004,
  "message": "对方不在线"
}
```

错误码定义：

| 错误码 | 含义 | 触发场景 | 是否断开连接 |
|---|---|---|---|
| 1001 | 用户名已存在 | 登录时用户名已被占用 | 否 |
| 1002 | 用户名非法 | 空、超长、含非法字符 | 否 |
| 1003 | 未登录 | 未登录就发送 LIST/BROADCAST/PRIVATE | 否 |
| 1004 | 对方不在线 | 私聊目标用户不存在 | 否 |
| 1005 | 消息太长 | 超过业务层上限 1 MiB | 否 |
| 1006 | 字段缺失或类型错误 | 业务处理时读不到必需字段 | 否 |
| 1007 | 类型不认识 | TYPE 未知 | 否 |
| 1008 | 协议层长度超限 | LENGTH > 4 MiB | 是 |
| 1009 | 魔数错误 | MAGIC 不匹配 | 是 |
| 1010 | 版本不支持 | VERSION 不认识 | 是 |

约定：

- 1001~1007：回复 ERROR，不断开连接。
- 1008~1010：直接关闭连接，不回复。

## 5. 编码约定

| 项 | 约定 |
|---|---|
| 文本编码 | UTF-8 |
| 字节序 | 网络大端序（LENGTH 字段用 htonl/ntohl） |
| JSON 库 | nlohmann-json |
| 二进制数据 | 用 std::string 存储，长度用 size()，不用 strlen |

---

## 6. 并发模型（协议层约定）

虽然并发属于实现细节，但为了双方理解一致，约定如下：

- 服务端采用**一连接一线程**模型。
- 在线用户表：`std::map<std::string, ClientInfo>`，key 为用户名。
- 在线表锁：一把全局 `std::mutex` 保护整个 map。
- 每连接发送锁：每个 `ClientInfo` 内一把 `std::mutex send_mutex`，防止多线程写同一连接时消息交错。
- 掉线清理：`recv` 返回 0 时，从在线表移除，关闭 fd。
- 心跳：暂不实现，后续可扩展。

---

## 7. 边界处理总结

| 情况 | 处理方式 |
|---|---|
| 一次收不全 | `recv_exact` 循环收，直到收满 |
| 长度超限（> 4 MiB） | 关闭连接 |
| MAGIC 不对 | 关闭连接 |
| VERSION 不认识 | 关闭连接 |
| JSON 解析失败 | 关闭连接 |
| 类型不认识 | 回复 ERROR 1007 |
| 业务内容超 1 MiB | 回复 ERROR 1005 |
| 对端关闭（recv 返回 0） | 从在线表移除，关闭 fd |
| SIGPIPE | 忽略信号或使用 MSG_NOSIGNAL |
| EINTR | 重试 |
