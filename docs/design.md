# 设计说明

## 阶段一：协议与并发

### 1. 帧结构选择
- **我选的帧结构**：方案 A（定长头 + JSON 负载）。
  具体布局：`MAGIC(2B) + VERSION(1B) + TYPE(1B) + LENGTH(4B) + PAYLOAD(JSON)`。
- **为什么这么选（和别的方案比，代价是什么）**：
  - 相比方案 B（一行一条文本），方案 A 有明确的 LENGTH 字段，能精确界定消息边界，不依赖换行符，能安全地传输大消息。
  - 相比方案 C（TLV），方案 A 多了 MAGIC 和 VERSION，能更快发现非法数据，并支持未来协议升级。
  - **代价**：头部固定有 8 字节开销，且 JSON 解析有性能损耗。但考虑到本项目规模，这些代价可接受。
- **两层上限**：
  - 协议层上限：4 MiB（保护内存，LENGTH 超限直接关闭连接）。
  - 业务层上限：1 MiB（产品规则，超限回复 ERROR 1005）。

### 2. 边界情况处理
- **一次收不全**：TCP 是字节流，`recv` 可能只给一部分。用 `recv_exact` 函数循环接收，直到收满头部 8 字节，再根据 LENGTH 收满负载。
- **长度超限**：解析头部时检查 LENGTH，若大于 4 MiB，直接关闭连接，不分配内存。
- **数据非法**：检查 MAGIC 和 VERSION，不匹配直接关闭连接；JSON 解析失败则回复 ERROR 1006。
- **类型不认识**：`switch` 分发时，`default` 分支回复 ERROR 1007，不断开连接，不崩溃。

### 3. 并发模型
- **模型选择**：一连接一线程。
- **为什么**：逻辑最直观，每个客户端的独立状态可以天然绑定到线程局部变量或 ClientInfo 中。避免了 poll/epoll 带来的事件驱动复杂度，便于调试。
- **在线用户表**：`std::map<std::string, ClientInfo>`，key 为用户名。
- **锁机制**：
  - 一把全局 `std::mutex` 保护整个在线表（增删改查）。
  - 每个 `ClientInfo` 内一把 `std::mutex send_mutex`，防止多个线程同时给同一个连接发消息导致字节流交错。
- **掉线清理**：`recv` 返回 0 时，从在线表移除，关闭 fd，线程退出。
- **心跳**：暂不实现。后续若需要，可增加 HEARTBEAT 类型。

### 4. 错误反馈
- 所有客户端请求，服务端都会给出明确响应（成功或 ERROR）。
- 错误码使用整数，具体定义见 `docs/protocol.md`。
- 严禁静默失败，严禁因异常数据导致服务端崩溃。
