# 传输速率测试设计与分析

## 1. 测试目标

- 在单机环境下，服务端能承受的最大数据传输速率是多少？
- 消息大小对传输速率的影响是什么？
- 群发和私发对传输速率的影响是什么？
- 探究不同编译模式（Debug/Release）及硬件环境对系统性能的影响?

## 2. 测试环境

| 项 | 值 |
|---|---|
| 服务端 | 虚拟机（Debian 12）/ 本机(WSL) |
| 客户端 | 虚拟机本机（127.0.0.1）/ 本机(WSL) |
| 编译器 | clang++ 14.0.6 |
| 消息编码 | JSON（UTF-8） |
| 协议层上限 | 4 MiB |
| 业务层上限 | 1 MiB |

## 3. 测试变量

| 变量 | 取值 | 说明 |
|---|---|---|
| 消息大小 | 1 KiB / 64 KiB / 1 MiB | 小 / 中 / 大 |
| 发送模式 | 私发 / 群发 | 单目标 / 多目标 |
| 接收者数 | 1（私发）/ 3（群发） | — |
| 发送者数 | 1 | 模拟"话痨" |
| 持续时间 | 10 秒 | 预热 2 秒后开始计时 |
| 编译模式 | Debug / Release | - |

## 4. 测试场景

| 编号 | 消息大小 | 模式 | 接收者数(不含自身) |
|---|---|---|---|
| A1 | 1 KiB | 私发 | 1 |
| A2 | 64 KiB | 私发 | 1 |
| A3 | 1 MiB | 私发 | 1 |
| B1 | 1 KiB | 群发 | 3 |
| B2 | 64 KiB | 群发 | 3 |
| B3 | 1 MiB | 群发 | 3 |

每组跑 3 次，取平均。

## 5. 测试指标

| 指标 | 定义 |
|---|---|
| 吞吐量 | 接收端每秒收到的字节数 |
| QPS（条/秒） | 每秒成功处理的消息条数 |
| 发送字节数 | 发送端每秒发出的字节数 |
| 接收字节数 | 接收端每秒收到的字节数 |

**以接收端的数据为准**，因为发送端可能只是把数据塞进了内核缓冲区。

## 6. 测试逻辑

1. 启动 1 个发送者，N 个接收者，全部登录。
2. 接收者开线程持续读取，统计收到的字节数。
3. 发送者持续发送固定大小的消息，持续 T 秒。
4. 计时结束后，统计：
   - 发送总字节数 / T
   - 接收总字节数 / T

## 7. 风险与干扰因素

|风险类别|说明|影响环节|
|---|---|---|
|**编译器优化**|`Debug` 模式（`-O0`）无优化，而 `Release` 模式（`-O3`）会进行内联、消除冗余拷贝等深度优化。`nlohmann::json` 是重度模板库，性能差距明显。|服务端和客户端|
|**硬件算力差异**|云主机通常为共享 vCPU，本机为物理多核 CPU。核心数和单核主频直接决定了并发处理和 JSON 序列化的速度。|服务端和客户端|
|**Python 脚本瓶颈**|压测脚本使用 Python 编写。在极高频发送/接收时（如 QPS > 1万），Python 的全局解释器锁（GIL）和动态内存分配会限制发送端的性能。|压测客户端|
|**TCP 协议机制**|高频发送 1 KiB 极小包时，极易触发 TCP 的 Nagle 算法和延迟确认机制，导致小包发送速率被物理网络机制限制。|网络链路|
|**锁竞争与线程切换**|服务端采用“一连接一线程”及互斥锁。在极高并发时，频繁的加解锁和操作系统线程上下文切换会消耗大量 CPU 资源。|服务端|
|**内核缓冲区**|内核 `SO_SNDBUF` / `SO_RCVBUF` 有上限。如果发送速度远超接收和处理速度，会触发 TCP 背压（阻塞 `send`）。|网络收发|

## 9. 结果分析
### 1. 编译模式与硬件算力的影响

- 在本机环境中，将编译模式从 Debug 切换为 Release 后，最大物理吞吐量突破 2.2 Gbps（1 MiB 群发）。这证明 `nlohmann::json` 的序列化/反序列化是极度依赖 CPU 算力和编译器优化的。
    
- 云主机受限于算力瓶颈，云主机（Debug）下的最大吞吐量仅为 34 Mbps。迁移至本机（Debug）后提升至 246 Mbps（提升 7.2 倍）。
    

### 2. 消息大小对系统表现的影响

- 无论在哪种环境下，1 KiB 的消息总能跑出最高的 QPS，但受限于协议头（8 字节）和 JSON 外壳的固定开销，总带宽不高；反之，1 MiB 的消息 QPS 极低，但有效载荷占比接近 100%，能将单次 I/O 的效率发挥到极致，从而测得系统的最高传输吞吐量。
    

### 3. 群发背压

- 内核背压：在群发模式下，发送端的灌入速率总是显著低于私发。因为服务端遍历多个目标、频繁加锁以及重复序列化导致处理变慢，使得发送端的内核缓冲区被塞满，`send` 调用被阻塞，从而强制压低了客户端的发送速率。
    

### 4. 异常现象分析

在 Release 模式下，场景 4（1 KiB 群发）的发送速率仅为 5.71 MiB/s，远低于场景 1（1 KiB 私发）的 139.85 MiB/s。出现该异常的可能原因是：

1. TCP Nagle 算法限制：高频发送小包群发时，触发了 TCP 的延迟确认机制，导致网络链路未能跑满。
    
2. 客户端 GIL 锁竞争：在群发场景下，Python 客户端的发送主线程和清理回显的接收线程在极高频下发生严重的 GIL 竞争，拖慢了客户端本身。

在本机测试中，Debug 模式和 Release 模式都出现 场景3（1 MiB 私发）吞吐量小于场景2（64 KiB 私发）吞吐量，出现该现象的可能原因是：

1. 内存分配与 CPU Cache Miss：64 KiB 足以把 8 字节的协议头和 JSON 外壳开销稀释且 64 KiB 的数据量可以较轻松地放入 CPU 的缓存中。1 MiB 已经突破了大部分 CPU 单个核心的 L2 缓存大小。这意味着当程序在频繁拷贝、序列化、反序列化 1 MiB 的字符串时，必须频繁地访问主存（RAM）
    
2. JSON 库在大字符串上的生命周期开销：`nlohmann::json` 解析 1 MiB 字符串时，内部不可避免地会产生深拷贝。大块的 `std::string` 分配和析构，伴随着操作系统内核的切换和页表更新开销。
